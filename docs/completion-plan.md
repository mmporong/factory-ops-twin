# Factory Ops Twin 완성 계약

## 사용자 목표

공장 렌더링과 실제 운영 상황의 표현까지 포함해 Factory Ops Twin을 AMR 시뮬레이션·디지털 트윈 직무용 포트폴리오로 완성한다. 사용자는 모든 남은 작업을 goal로 진행하고, 최종 렌더 장면에서 유효한 데이터와 미디어를 생성·관리할 것을 명시했다. 기존 G0a/G0b/G1/G2와 G3 정상 FIFO 두 주문 qualification은 보존한다. 기준 커밋은 337c4c75fd52e17651d8eff1ab2033247132c82f다.

완성품의 최종 차량 수는 사용자 최신 요청에 따라4대다. 기본 운영·파일럿·정책 비교·대표 미디어는4대로 구성하고,1대·2대는 개발 중 검증 단계로 사용한다.4대의 실제 물리·센서·운영 검증 통과를 완료 조건으로 삼는다. 현재 검증된2대와 최종 목표4대를 구분해 보고한다.

## 에즈웰플러스·딜로이트 공통 대응과 차량 수의 역할

최신 범위는 최종4대와3D 웹 운영 대시보드다. Next.js·React Three Fiber 화면에서 AMR·토트·설비를 선택하고 실제 원장/API의 작업·적재물·목적지·속도·SOC 원천·대기 이유를 확인한다. 물리·주행·센서의 권한은 Isaac Sim/ROS에 남기고, 웹의 요청은 지원 capability·버전·명령 ID를 검사한 뒤 처리한다. local_model/replay/live와 stale·명령 접수/실행 결과를 구분한다. SOC·유한 SKU 재고가 물리 임무에 연결되기 전에는 미연결/미관측으로 남긴다.

웹은 Kit 익스텐션의 대체 완료 근거가 아니다. 둘은 같은 운영 데이터 계약을 재사용한다. 합성 데이터 생산은 기존 Isaac Sim Replicator에서 수행하고 웹은 조건 선택·요청·진행/결과·라벨/QA 조회를 담당하도록 연결한다. GPU 수집/검증 handler를 붙이기 전에는 촬영 실행을 활성화하지 않는다. 이 범위는 기존 goal의 완료 계약에 합치며 과거8대 계획·과거 실행 원본을 현재4대의 성공 자료로 바꾸지 않는다.

## 현재 우선순위 — 사용자 조정 반영

1. 두 AMR의 실제 임무 완주, 가감속·회전·정지, 공유 통로 대기와 복구를 먼저 구현한다. 기능이 막힌 상태에서 데이터 수량을 늘리거나 중간 독립 리뷰를 반복하지 않는다.
2. 40×24 m 시험 배치의 빈 공간과 과도하게 큰 설비 표현을 개선하는 32×20 m 생산 구역 후보를 구현한다. 자재 보관·키팅, 조립·검사, 포장·출하를 연결하며, 촬영 구도만 좁혀 개선했다고 주장하지 않는다. 물리 배치 변경 시 지도·경로·센서도 같은 버전으로 갱신한다. 새 배치의 정상 임무 완주·조감 렌더와 보정 카메라의 CI 구간 촬영을 확인했다. 후속 GPU 실행에서 시각 상태14개 전부의 순차 적용을 확인했으나 정지 후 도착 검사에서 실패했다. 움직이는 상태의 조기 성공을 막는 도착·정지 연결을 수정했으며 새 GPU 전체 검증·폐쇄/복구가 남아 있다.
3. 기존 합성 데이터 1,080장은 보존하고 추가 생산하지 않는다. 다음 실행의 정기 RGB는 600물리 스텝(60Hz에서10초) 간격으로 줄이고, 시작/종료·물류 상태 변화를 남긴다. 신규 생산 구역의 진단 실행에서는 연속 영상 촬영을 기본으로 끈다. 주행이 안정된 뒤 최종 미디어 실행에서만 한 번의24초 동작 구간을 켠다. 원인 분석과 실제 동작 판정에 필요한 로그는 유지한다.
4. 대량 비교 실행과 최종 미디어 제작은 완주 로직·생산 구역이 안정된 뒤 진행한다. 아래 G004의 수량은 확보한 과거 데이터의 범위이며 새로운 장면을 바꿀 때마다 다시 채워야 하는 조건으로 쓰지 않는다.

물리 적재의 완료 증거에는 적재물의 질량·충돌과 지지/고정 상태, 도킹 정렬, 적재/하역 확인, 운반 중 미끄러짐·낙하·간섭 검사가 필요하다. USD 표시 위치 변경이나 논리적인 owner 변경만으로 물리 적재를 통과 처리하지 않는다. 공급자 제품의 공개 제원을 참고한 자체 차량은 공급자의 인증된 디지털 트윈으로 표현하지 않는다.

증설은 차량 형식과 적재 방식을 정한 뒤 단일 차량의 빈차/적재·정렬 시험, 새 구성의2대 정상/폐쇄·복구,최종4대 혼합 운영 순서로 진행한다. 기존2대 소프트웨어와 관측 수정은 재사용하되, 새 차체에서 기존 충돌 반경·지도·센서 검증을 그대로 인정하지 않는다.4대의 실제 작업 수요와 공정·인계 처리량을 설정하고, 주차·충전·대기 위치, 버퍼 용량과 교차·합류 경로를 지도와 함께 설계·검증한다. 기존32×20m 배치의 수용성은 이 조건으로 다시 판단한다. 부하 증설을 이유로 통로 점유나 정지 확인 조건을 완화하지 않는다.

4대 완료 판정에는 서로 다른 로봇4개와 ROS namespace·TF·센서·주행 허가·예약·작업 원장이 결속되어야 한다. 시나리오 묶음에서4대 각각이 실제 운송 작업을 수행하고, 자재 공급·완제품 출하·재보충·빈 토트 회수 및 충전 대기/복귀가 혼합되어야 한다. 같은 실행의 실제 촬영과 원장으로 이를 증명하며, parked 차량의 단순 표시나 화면상 복제로 참여 대수를 채우지 않는다.

6개 파일럿은 최종 차량·운영 모델·4대 구성을 고정한 뒤 정상/폐쇄/주문 급증 × FIFO/ETA로 수행한다. 현재2대용 미실행 입력을 최종4대 비교로 해석하지 않는다. 기존 v4 프로토콜·설정은 과거 계획으로 보존하고, 변경된 모델의 소스·배치·작업 수요·대수·충전·재고 조건을 새 실행 프로토콜에 결속한 후 사용한다.60회 비교도4대를 기준으로 하며, 파일럿에서 비용·용량·실행 가능성을 확인한 뒤 착수한다.

증설 중1→2→4대에서 완료율·처리량·대기·교착/복구·충전 대기와 RTF·센서 발행률·CPU/RAM·VRAM·원본 크기를 측정한다.4대가2대보다 유리하다고 가정하지 않으며, 최종 완료 조건은4대의 센서·안전·운영 검증 통과다. 자원 부족 시 병목 최적화·장면/기록 구성·실행 환경의 대안을 확인하고 승인된 예산과 권한 안에서 해결한다.60회 정책 비교에 차량 수 축을 추가해240회로 늘리는 것은 현재 계획에 포함하지 않는다.

다음 실행 순서: 저장 공간 확보 → 차량·적재 및 재고/반납/충전·4대 registry의 로컬 구현 → 단일 차량 물리 검증 →2대 기준선과 폐쇄/복구 →4대 정상/폐쇄/급증·충전 운영 →4대 구성의6개 파일럿 → 가능한 자원 안의비교·최종4대 미디어. GPU는 실제 물리 검증 시점에 기동하고 진단 중 연속 촬영은 계속 끈다.

## 단계별 결과

G001: 주차 점유와 후속 경로가 겹치는 교차 배정의 진행성 문제를 수정한다. 작성된 16사례와 실제 배차 회귀시험으로 증명하며, retained hold와 정지 확인 계약을 보존한다.

G002: 40×24 m 가상 산업용 센서 모듈 공장에 설비 외형·랙·토트·팔레트·작업 구역·안전 표시·조명을 갖춘 재현 가능한 USD 시각 층을 구현한다. 픽업·드롭·버퍼·공정·출하 상태를 운반물·설비 표시와 연결하고, 카메라/조명/재질을 구성한다. 무료 에셋은 공식 출처·라이선스·SHA와 함께 참조하며 유료 구매는 하지 않는다.

G003: 최종 산업 장면을 GPU에서 렌더하고, 충돌 외곽·지도·LiDAR·AMR footprint·가감속·회전/정지의 정합성을 검사한다. 최종4대의 혼합 물류·공유 통로 대기·폐쇄 우회와 복구·충전 운영을 새 차량/장면에서 촬영·검증한다. 단일/2대는 중간 검증으로 구분하고 실패 실행도 별도 ID로 보존한다.

G004: 최종 장면에서 RGB/Depth/semantic/instance/bbox/카메라 정보를 수집·검사하는 경로를 완성한다. 장면 seed·배치/물체/조명/카메라 조건을 달리한 최소 12개 독립 장면에서 장면당 최소 30개 촬영 시점·3개 시점의 대응 자료를 생성한다. 최소 1,080개 RGB에 연결된 유효 modality를 확보하고, 가림·화면 밖·클래스/instance ID·좌표·투영·깊이 무효값·파일 해시를 검사한다. 독립 scene ID 단위 train/validation/test 분할과 별도 시각 검수 결과를 남긴다. 반복 프레임을 독립 장면으로 세거나 모델 학습 성능을 가장하지 않는다.

포트폴리오 데이터의 완료 판정에는 최종 profile의 `deterministic_data_passed`와 별도 AI 시각 검수의 `portfolio_qa_passed`가 모두 필요하다. AI 검수는 실제 RGB·capture·camera·leaf 가림 자료와 protocol SHA에 결속된 외부 sidecar로 남긴다. 사람의 릴리스 승인과 생산용 승인 상태는 별도로 보존하며, AI 검수를 이 두 승인이나 물리 접촉 증거로 해석하지 않는다. 원본 `visual-review.json`을 수정해 미검수 자료를 승인 자료로 바꾸지 않는다.

G005: 현재 cloud 가격/가용 크레딧과 실제 wall time·RTF·VRAM·CPU 검증 메모리·원본/압축 데이터량을 확인한다. 최종4대의 부하 보정과 정상/폐쇄/주문 급증 × FIFO/ETA의6개 파일럿을 실제 실행한다. 이후 평가 입력·자원 예산을 고정한다.

G006: 최종4대로 정상/폐쇄/급증 × FIFO/ETA × 10 seed의60개 평가 입력을 실행하고 실패·미완료도 포함해 짝지은 정책 비교를 완성한다. ETA의 우월함을 전제하지 않으며, 실제 결과에 따라 완료 주문·운반/대기 시간·버퍼/통로 병목을 설명한다. 실행 환경·소스·설정·원장·ROS bag·미디어가 연결되어야 한다.

G007: 최종4대 장면의 실제 촬영으로 대표 이미지, 원속도 동작 구간, 운영 전체 영상, 예약/주문/버퍼/충전 상태와 원인을 설명하는 포트폴리오 미디어를 만든다. README의 프로젝트 전체 상태·설치/실행법·검증 범위·대표 미디어를 갱신하고 데이터/에셋/결과 출처와 한계를 명시한다. 검증한 변경을 커밋·push하고 원격 SHA를 대조한다.

G008: 변경 동작에 필요한 검사와 최종 code-reviewer 또는 verifier의 통합 검수 1회를 완료한다. 사용자 요청에 따라 중간 독립 리뷰와 반복 승인 절차를 늘리지 않는다. 최종 원본/미디어/데이터/소스 bundle을 서로 다른 저장소에 백업하고 실제 복원·정확한 파일 집합·크기·SHA 검사를 통과한다. 작업 프로세스·컨테이너를 정리하고 Brev STOPPED를 확인한 뒤에만 aggregate goal을 완료한다.

## Architecture invariants

- 실제 Isaac Sim 실행의 센서·물리·ROS·운영 원장을 근거로 한다. 생성 이미지는 구상 설명용이며 실행 증거를 대신하지 않는다.
- GT는 사후 평가·라벨·미디어에만 사용한다. 배차·Nav2·예약은 추정 위치·센서·현재 상태를 사용하고 미래 해제 시각을 미리 알려주지 않는다.
- retained occupancy, atomic transfer, stale fail-closed, accepted goal UUID/Path/예약 세대/주행 허가, 물리 HOLD ACK와 신선한 연속 정지, 마지막 frame/ROS stamp 및 닫힌 bag의 결속을 유지한다.
- 기존 원본·실패 보고서·아카이브를 수정하거나 새 결과로 덮어쓰지 않는다. 실행 attempt·run ID·물리/검사기/시각 장면 버전을 구분한다.
- 새 시각 형상은 단위·좌표·물리 envelope·센서 관측·지도와 정합해야 한다. 형상이 이 경계를 바꾸면 지도·센서·주행을 재검증한다. 주차 문제를 가리기 위해 통로를 넓히거나 점유를 조기에 해제하지 않는다.
- 운반물·공정 애니메이션의 논리 상태 연결과 실제 물리 적재/파지 검증을 구분한다. 이 프로젝트는 현장 CAD/MES와 동기화한 실공장의 복제가 아닌 가상 공장의 시뮬레이션이다.
- 렌더 완료 후 촬영 자료의 동기화·클래스·instance·bbox·깊이·카메라·source SHA를 검사한다. 영상은 원본 시각 자료를 대체하지 않는다. 장면 간 데이터 누출을 막고 QA 실패 자료는 승인 데이터에서 분리해 보존한다.
- 하나의 기존 승인 AWS L40S 인스턴스를 사용한다. 과거 약 400 USD 크레딧을 현재 잔액으로 단정하지 않으며, 확인된 사용 가능 예산을 넘기지 않는다. 유료 에셋 구매·새 결제수단·실물 로봇 구동·외부 알림은 범위에 넣지 않는다.
- GPU가 필요한 시점에만 기동한다. 각 실행 묶음 뒤 백업/검증/Stop을 수행하며, 저장 공간·비용이 모자라면 측정 근거와 가능한 대안을 기록하고 승인된 한도를 넘어 실행하지 않는다.
- 프로젝트 런타임 의존 패키지는 명시적 필요와 승인 없이 늘리지 않는다. Git에는 코드·설정·문서·작은 대표 미디어와 색인만 보관하고 대형 에셋·원본 데이터·인증 정보는 넣지 않는다.

## 완료 판정

4대의 실제 물리·센서·혼합 운영과 최종 렌더 장면, 실제 비교 평가, 유효 데이터와4대 포트폴리오 미디어, 원격 저장소·백업·Stop 및 독립 검수가 모두 충족되어야 한다. 웹의 선택·상태 동기화와 지원된 조작 결과도 같은 원장으로 검증한다. 중간 단계나 실패한 검사·미실행 입력을 완료로 표시하지 않는다. 예산/자격증명 등 외부 제약이 남으면 목표를 완료 처리하지 않고 근거와 남은 일을 기록한다.

## 실행 방식

Codex 기본 goal을 사용하고 일반 구현·검증으로 수행한다. ultragoal의 Conductor 인계는 현재 호스트의 권한 증명 제약으로 사용하지 않는다. 원래 brief와 8개 작업의 완료 조건은 보존하며, 기본 goal을 전체 결과가 검증되기 전에 완료 처리하지 않는다.
